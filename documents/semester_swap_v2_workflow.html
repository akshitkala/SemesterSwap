Authentication & Session Flow

1
User clicks "Sign in with Google"
Browser opens Firebase Google OAuth popup. User selects their Google account.
Frontend — Next.js Firebase Auth SDK
2
Firebase returns Google ID Token
Firebase verifies Google credentials and issues a signed ID Token (JWT) containing uid, email, displayName. Valid for 1 hour.
Firebase Auth — Google ID Token (JWT)
3
Frontend sends POST /api/auth/login
Frontend forwards the Firebase ID Token in the Authorization: Bearer header to the Express backend.
4
Auth Middleware — Firebase Admin SDK verification
Backend calls Firebase Admin SDK verifyIdToken(token). Decodes uid, email, displayName from the claims.
❌ Invalid / Expired Token
Returns 401 Unauthorized
Request rejected immediately
✓ Valid Token
Proceeds to DB lookup
uid, email attached to request
5
MongoDB — User lookup by firebaseUid
Backend queries Users collection for a document matching the decoded firebaseUid.
🆕 First Login
Auto-create User document
role: 'user', isActive: true
Store email + displayName
↩ Returning User
Fetch existing document
Read role + isActive
6
isActive check — Ban gate
Auth Middleware reads isActive from the fetched User document.
🚫 isActive: false (Banned)
Returns 403 Forbidden
Blocked even with valid token
✓ isActive: true
req.user = full User document
Proceeds to Role Middleware
7
Session established — User object returned
Backend returns the user document (excluding firebaseUid). Frontend stores session state. Role determines which UI routes and API calls are accessible.
_id · email · displayName · role · isActive
🔐 Security Notes
⚡
firebaseUid is never returned in any API response — internal identifier only.
⚡
Token expiry is handled by Firebase (1 hour). Frontend must refresh the token silently before it expires.
⚡
Every protected request runs steps 4–6 in Auth Middleware — not just login. A ban takes effect within milliseconds.

Edit & Delete Rules

✏ Edit Own Listing
User can edit any field
If status was 'approved' → resets to 'pending'
Listing disappears from public view until re-approved
Goes back into Admin pending queue
🗑 Soft Delete Own Listing
Sets isDeleted: true
Hidden from all public queries immediately
Data retained in DB for audit purposes
Admin can still see it in raw queries
⚡ Automatic Mode
New listing → status: approved instantly
Skips Admin queue entirely
AdminActivity logged: AUTO_APPROVE_LISTING
actor: null, actorType: 'system'
🔒 Manual Mode (default)
New listing → status: pending
Requires Admin approve/reject
Switching mode does NOT affect existing listings
Only new listings created after toggle are affected

Request Middleware Stack — Every Protected Route

MIDDLEWARE 01
Auth Middleware
Extracts Bearer token → verifies with Firebase Admin SDK → decodes uid → fetches User from MongoDB → checks isActive
401 — missing/invalid token
403 — isActive: false (banned)
MIDDLEWARE 02
Role Middleware
Reads req.user.role → checks against required role for the route → enforces hierarchy user < admin < super_admin
403 — insufficient role
MIDDLEWARE 03 — POST /api/books only
Approval Mode Middleware
Reads SystemConfig.approvalMode from DB → if 'automatic': sets status to 'approved' + logs AUTO_APPROVE_LISTING with actorType:'system', actor:null → if 'manual': sets status to 'pending'
ROUTE HANDLER
Business Logic
Validated request reaches the actual route handler. Input validated with Joi/Zod before DB operations.

Ban Enforcement — Two Layers

1
Super Admin triggers ban
PUT /api/super-admin/users/:id/toggle-status — sets isActive: false in MongoDB.
2
Layer 1 — Firebase token revocation
Backend immediately calls Firebase Admin SDK revokeRefreshTokens(firebaseUid). The user's existing token is invalid at the Firebase level.
3
Layer 2 — isActive check on every request
Auth Middleware checks isActive on every request. Returns 403 even if the user somehow presents a token before Firebase propagates. Zero gap window.
